# teaspoon (tsp)

Standalone Rust tooling for deterministic, loss-aware mining of Outlook `.pst` and `.msg` files.

Shorthand for teaspoon (i.e. the name of this project) is tsp (i.e. the name of this project's tool), which is "pst" backwards. (ツ)

`tsp` inspects Outlook mail containers (`.pst` files, single `.msg` files, or a directory of `.msg` files) and prints a **privacy-safe inventory**: counts and structural facts only. It never prints message bodies, subject lines, sender/recipient addresses, attachment names or bytes, folder names, file paths, or any other free-form content. Its output is designed to be safe to share and safe to diff across versions. Since M4c it can also **export** `.msg` input to a Markdown archive in a directory you name (since M4d including the sender, recipients, date, and other envelope fields, and since M4e-2b the message body as Markdown together with the original body forms, and since M4f-1 the by-value attachments as files, and since M4f-2a the embedded messages as nested message folders, and since M4f-2b the `cid:` links in `message.md` pointing at the extracted attachment files); the archive holds message content, but what `tsp` prints stays counts-only.

**M0 — architecture/research baseline:** established. All seven original ADRs are Accepted. ADR "Custom MS-OXMSG parser graduates to the production MSG path" moved from Proposed to Accepted when M3f shipped. ADR "Independent differential verification" now records the MSG-side verification actually performed; the PST-side comparison against an independent implementation has not been run. Four further ADRs, drafted in M4a-2 and **accepted on 2026-10-04**, complete the archive ADR: export naming, collisions, and path budgets; message and folder identity and provenance; export output posture, consent, and ownership; and the archive file contract and schema evolution. Two more ADRs, accepted in October 2026, decide the HTML-to-Markdown converter and preprocessing and the body selection, original bodies, and formatting-loss recording. Part of the identity ADR is a decision without code yet (PST identifiers and the content hash are not written by any code). One more ADR, drafted in M4f-1 and accepted when the owner committed it, decides attachment extraction: the chunked copy, the per-attachment records, and what happens when an attachment cannot be read. It was amended in M4f-2 (2026-10-20) with the embedded-message decisions: nested message folders, the record of one at the depth cap, the counters, and the byte-level differential; and in M4f-2b (2026-10-21) with the `inline` marking and the rewriting of `cid:` references. **M1 — PST feasibility spike: complete**, within the limits of `outlook-pst` v1.2.0's public API. A small read-only CLI (`tsp`) exercises the Microsoft Rust PST implementation: open a PST, reach the message store/IPM subtree, traverse folders, enumerate messages, and inspect raw message properties, plus aggregate message-class, body-availability, recipient-count/type, and attachment-count/classification diagnostics — all without emitting any message content.

- P1 through P4b are done and verified on Windows against a real PST fixture deliberately enhanced to cover plain/RTF bodies, a BCC recipient, an embedded-message attachment, and an OLE attachment — see `docs/verification/m1-results.md`.
- Zero-byte and by-reference attachments were explicitly excluded as fixture goals (empirically impractical to compose / obsolete in modern email) — see `docs/verification/m1-results.md` for the documented rationale. The classification code for both remains.
- Opening/traversing embedded-message or OLE attachment *content* was investigated (P4c) and found not achievable through `outlook-pst` v1.2.0's public API — accepted as M1's practical ceiling, not a defect. `tsp` correctly detects and counts these attachments on the PST side; it can't open them.
- HTML-in-RTF detection (MS-OXRTFEX `\fromhtml1` encapsulation) is implemented and confirmed correct against real data — see `docs/verification/m1-results.md`.

This is deliberately **not** the production miner: the PST path only counts, and attachment content is not extracted.

**M2 — MSG ingestion spike: complete.** `tsp` dispatches on its input: a `.pst` file uses the PST path; a single `.msg` file or a directory of `.msg` files (scanned non-recursively) uses the MSG path. M2 built that path on the `msg_parser` crate, mirroring M1's structure. Body-type detection, recipient/attachment classification, and the zero-byte/subdirectory-visibility fixes were all confirmed correct against real data. Opening an embedded-message attachment as a nested message (M2c) was investigated across two independent real attempts and found not achievable through `msg_parser`, for a root cause never identified. That ceiling was later removed by the custom parser (M3e). See `docs/verification/m2-results.md` for the full evidence trail.

The custom MS-OXMSG parser decodes real property values — not just structure — and is now the **default** `.msg` path. See `docs/verification/m3-results.md` for the full evidence trail of M3, including the run commands and the field-by-field diff table.

`msg_parser` remains a normal (non-dev) dependency, because the `--verify` and `--verify-envelope` differential harnesses ship in the binary. It is the **oracle only**: no default code path calls it, and there is deliberately no runtime fallback flag.

## Design principles

1. `.pst` and `.msg` are input formats, not the domain model.
2. Format adapters produce a common Outlook-item representation.
3. Markdown is a projection, not the canonical representation.
4. Unknown/unmapped properties are preserved or reported rather than silently discarded.
5. Extraction loss is explicit.
6. Source provenance is part of the output model.
7. Evidence distinguishes specification support, implementation support, tests, and independent verification.

## Build and run

```
cargo run --release -- .\sample.pst
cargo run --release -- .\folder-of-msgs\
cargo run --release -- .\sample.msg
cargo run --release -- --verify .\folder-of-msgs\    # differential check against msg_parser + structural gates
cargo run --release -- --verify .\sample.msg
cargo run --release -- --verify-envelope .\folder-of-msgs\   # envelope (subject, sender, recipients) vs msg_parser
cargo run --release -- --verify-envelope --recursive .\folder-of-msgs\   # ... including subdirectories
cargo run --release -- --verify-deencap .\folder-of-msgs\    # RTF de-encapsulation vs msg_parser's html_from_rtf (M4e-1)
cargo run --release -- --verify-deencap --dump-deencap .\dump .\folder-of-msgs\   # also write both HTML strings and the RTF per message to .\dump
cargo run --release -- --verify-bodies .\folder-of-msgs\   # M4e-2c: does the Markdown keep every visible word of the HTML, in order? (counts only)
cargo run --release -- --verify-bodies --recursive --dump-bodies .\words .\folder-of-msgs\   # also write the two word lists of each message with a difference to .\words
cargo run --release -- --verify-attachments .\folder-of-msgs\   # M4f-2c: are the extracted attachment bytes the ones msg_parser sees? (counts only)
cargo run --release -- --verify-attachments --recursive .\folder-of-msgs\   # ... including subdirectories
cargo run --release --features bakeoff -- --bakeoff-md --bakeoff-dump .\md .\dump   # M4e-0: HTML-to-Markdown bake-off over a --dump-deencap directory
cargo run --release -- .\sample.pst --out .\tsp-out --dry-run        # plan an export; print the naming census
cargo run --release -- .\folder-of-msgs\ --out .\tsp-out --dry-run
cargo run --release -- .\sample.msg --out .\tsp-out                  # export (.msg input only so far)
cargo run --release -- .\folder-of-msgs\ --out .\tsp-out --overwrite
```

`cargo test` runs the unit tests: classification, decoding (including the `PT_STRING8` code page chain and synthetic ANSI `.msg` fixtures built at test time), counters, every verify-comparison outcome, the structural gates, the naming and planning rules (including property tests), the body pipeline (selection, preprocessing, padding, loss, and the real converter), the archive renderers (against committed golden files in `tests/golden/`, including an envelope-rich message), the envelope comparison rules, the body-form reader, and the export writer (against synthetic `.msg` files built at test time, including native-HTML, RTF-only, failure cases, and by-value attachments: large, empty, duplicate-named, unnamed, with missing data, and by other methods, with their `cid:` links rewritten; and the stager's chunked copy of a stream, which must equal a whole-file add and survive short reads, an interrupt, an empty source, and a failing source).

One test is gated on a local corpus. Real `.msg` fixtures are deliberately not in this repository, so `fixture_corpus_verify_is_clean` runs only when `TSP_FIXTURE_DIR` points at a directory of `.msg` files, and otherwise skips with a note:

```
$env:TSP_FIXTURE_DIR = "C:\path\to\msgs"
cargo test fixture_corpus_verify_is_clean -- --nocapture
```

It asserts zero mismatches on every comparable field and zero on every structural gate, allowing exactly the documented RTF-dictionary divergence. Failure messages carry counts only, never content. (It covers `--verify`; `--verify-envelope` is run by hand.)

The memory gate's synthetic corpus comes from an ignored test: set `TSP_BIG_CORPUS_DIR` to a new directory and run `cargo test --release generate_a_large_synthetic_corpus -- --ignored`. `TSP_BIG_COUNT` (default 200) is the number of messages, `TSP_BIG_MB` (default 2) the size of each message's HTML and plain-text bodies, and `TSP_BIG_ATTACH_MB` (default 0, none) adds one by-value attachment of that many megabytes to every message (use a small `TSP_BIG_COUNT` with it, since each message carries its own copy). Measure with `measure-peak.ps1`: the peak working set should not grow with the message count or with the attachment size.

Input may be:

- a `.pst` file — full PST diagnostic (and `--dry-run`; export is not implemented),
- a `.msg` file — MSG diagnostic through the custom MS-OXMSG parser,
- a directory — every `.msg` file directly inside it is scanned  
(non-recursive; skipped subdirectories are reported as  
`subdirectories_skipped`). With `--dry-run` or an export, a directory is instead handled **recursively**, mirroring its subdirectories as folders, down to 64 levels; directories below that are counted (`source_directories_beyond_depth_cap` in a dry run, `export_source_directories_beyond_depth_cap` in an export), not silently skipped.

Real PST/MSG fixtures are required to perform the behavioral portion of any milestone. No personal mail data is embedded in this repository.

CI (`.github/workflows/ci.yml`) runs format, check, clippy (`-D warnings`), test, and a release build on Linux and Windows, with `--locked`; `docs/CONTRIBUTING.md` defines the gate. It cannot exercise real PST/MSG parsing, because the fixtures are excluded from the repo, so the corpus-gated test and the fixture runs remain a manual step on a machine that has the fixtures.

## Modes

| Command | What it does |
|---|---|
| `tsp <input>` | Default diagnostic: PST input uses the PST path; `.msg` input uses the custom MS-OXMSG extraction path. |
| `tsp --verify <msg input>` | Differential verification: runs the custom extraction path and `msg_parser` (the oracle) over the same files and prints match/mismatch counts per field — never the values compared — followed by the custom path's structural gate counters and `structural_gate_violations`. When any gate is nonzero, a `structural_breakdown=follows` marker and the privacy-safe structural breakdown are printed as well, to make the violation triageable. |
| `tsp --verify-envelope <msg input>` | Envelope differential verification (M4d): compares the envelope the export writes (subject, sender name and email, the To/Cc/Bcc lists with each recipient's name and email) with `msg_parser`, field by field, and prints match/mismatch counts only. For each email it reports which of the custom path's two properties (`PidTagEmailAddress` or the SMTP address) equalled the oracle's string. Also prints presence counts for the fields `msg_parser` cannot supply (sent-representing, times, importance, sensitivity, conversation fields, transport headers). Scans a directory non-recursively. Cannot be combined with `--verify`, `--out`, or `--dry-run`. |
| `tsp --verify-deencap <msg input>` | De-encapsulation differential verification (M4e-1, complete: recognition and presence agree with `msg_parser`; every difference in the recovered HTML was traced to `msg_parser`): for each message, recognizes encapsulated HTML by the MS-OXRTFEX 10-token rule, recovers the HTML with the in-house de-encapsulator, and compares it with `msg_parser`'s `html_from_rtf()` in graded steps (identical, equal ignoring whitespace, equal ignoring whitespace and non-ASCII, same visible text, different), plus the recognition rule against the whole-document `\fromhtml1` search. Prints counts, flags, code page numbers, and byte-size differences only. Cannot be combined with `--verify`, `--verify-envelope`, `--out`, or `--dry-run`. |
| `--dump-deencap <dir>` | With `--verify-deencap`, writes for each message `NNN.custom.html`, `NNN.msg_parser.html`, and `NNN.rtf` (the decompressed RTF) into `<dir>`, where `NNN` is the message's position in the scanned list, so a pair can be compared locally. The directory must be new or empty. This is the only place message content goes; standard output stays content-free and no file name comes from the message. |
| `tsp --bakeoff-md [--bakeoff-dump <dir>] <dir>` | HTML-to-Markdown bake-off (M4e-0; first run 2026-10-10: no candidate failed, `htmd` default mode leads, and it was then chosen by the converter ADR). Needs a build with `--features bakeoff`, which compiles in the candidate converters (`htmd`, `html2markdown`, `html-to-markdown-rs`). Runs each over the `NNN.custom.html` files in `<dir>` (the `--dump-deencap` output) and a built-in set of synthetic cases, and prints content-free scores: panics, errors, nondeterminism, visible words missing, structure kept, noise left. `--bakeoff-dump` saves each candidate's Markdown locally for review. |
| `tsp --verify-bodies <msg input>` | Content-preservation check (M4e-2c; `v0.1.32`; 0 differences over the 31 HTML bodies of the corpus). For each message whose selected body is HTML (native, or recovered from the RTF) it runs the export's own preprocessing and conversion and compares, in order, the visible words of the HTML with the words of the Markdown. Prints counts only: words in each, words matched in order, words missing from the Markdown, extra words in it, Markdown syntax words excused, the messages with a difference (by position in the scanned list, with their missing, extra, and run counts), and `body_check_gate_violations` (0 expected). HTML words: the text outside tags after the production preprocessing, without the content of a closed `head`; entities decoded (a named entity outside the built-in table is counted, not guessed); block elements and `br` separate words, inline elements join them. Markdown words: link text kept, link destinations and image alt text and destinations dropped, backslash escapes undone. On both sides the emphasis and code characters (asterisk, underscore, tilde, backtick) and the invisible padding characters are removed from every word. Markdown syntax words (runs of hash, greater-than, hyphen, plus, vertical bar, colon, or equals characters, and ordered-list numerals such as `1.`) are excused only where they do not match the HTML's next word. The comparison is greedy and in order (window of 64 words), so a non-zero count is approximate and zero is exact. Cannot be combined with the other verify modes, `--out`, or `--dry-run`; `.msg` input only. |
| `--dump-bodies <dir>` | With `--verify-bodies`, writes `NNN.html.words.txt` and `NNN.markdown.words.txt` (one normalized word per line, `NNN` the message's position in the scanned list) for every message with a difference into `<dir>`, which must be new or empty. This is the only place message content goes. |
| `tsp --verify-attachments <msg input>` | Attachment payload differential (M4f-2c; `v0.1.35`; 30 of 30 matches on the corpus). For each top-level by-value attachment, hashes the bytes the export would write (through the export's own reader, in chunks) and compares the SHA-256 and length with `msg_parser`'s payload for the attachment at the same position in storage order. Prints counts only: attachments on each side, matches and mismatches, missing or unreadable streams, positions where the two disagree on the method, the same comparison with the order ignored, bytes matched, and `attachment_payload_gate_violations` (0 expected). Embedded messages are not opened. `.msg` input only; cannot be combined with the other verify modes, `--out`, or `--dry-run`. |
| `--recursive` | With `--verify-envelope`, `--verify-deencap`, `--verify-bodies`, or `--verify-attachments`, scans a directory input down to 64 levels instead of only its top level; directories below that are counted in `subdirectories_skipped`. |
| `tsp <input> --out <dir> --dry-run` | Plans an export of the input into `<dir>` without writing anything, and prints content-free counts (`plan_*` for the plan and its gates, `source_*` for facts about the source, `folder_identity_*` for PST folder identity availability). Shows how many names need sanitizing or shortening, how many collide, the longest planned path against the Windows budget (259 UTF-16 units), and whether any gate is violated. |
| `tsp <msg or dir> --out <dir>` | Exports `.msg` input to `<dir>/<input name>/` (see Export below). Prints counts only (`export_*` keys, plus the plan keys). Exit code 0 on success, 2 when it refused and wrote nothing, 1 on an error. `.pst` input stops with a "not implemented" error. |
| `--overwrite` | Consent, without asking, to replace files that an earlier export by `tsp` generated and that this export would change. Without it, `tsp` asks (interactive terminal) or refuses with exit code 2 (not interactive). |
| `--no-source-hash` | Do not record the SHA-256 of the source in the archive root's `folder.json`. |

The transitional `--oxmsg` (structural diagnostic) and `--extract` (alias of the default) flags were removed in M3g. Passing either is a command-line error.

## Export (M4c, envelope since M4d, body since M4e-2b, by-value attachments since M4f-1, embedded messages since M4f-2a, `cid:` links since M4f-2b)

`tsp <msg|dir> --out <dir>` writes:

```text
<dir>/<input name>/
  folder.json            archive root: marks the directory as created by tsp, source (kind, name, size,
                         optional SHA-256), counts, status (incomplete while running, complete at the end)
  <subdirectory>/        one per mirrored subdirectory, each with a folder.json
  <subject>/             one directory per message, named from its subject (sanitized, shortened, numbered
    message.md             if names collide)
    metadata.json
    body.html              the original body forms, each only if the message has it (byte copies)
    body.rtf
    body.txt
    attachments/           by-value attachments, one file each under its planned name (since v0.1.34); embedded messages as nested message directories (since v0.1.35)
```

A worked example, with the draft file contents, is in `docs/examples/m4c-example-archive.md`. The rules behind it are the accepted ADRs in `ADRs/`: naming and path budgets, identity and provenance, output posture and consent, the archive file contract, the converter, and body selection and loss.

- `message.md` is the subject as a heading, then a list of the envelope fields the message has — From, On behalf of, To, Cc, Bcc, Date (UTC, from the sent time, else the delivery time), Importance, and Sensitivity (the last two only when not the default) — then the body. The body is the first of: the native HTML converted to Markdown; the HTML recovered from the RTF, converted; the plain-text body verbatim inside a code fence; nothing. Conversion is `htmd` after preprocessing (comments, `style`, `script`, `title`, Word's downlevel markers and `o:p` tags are removed) and a rule that removes long runs of invisible padding characters from the Markdown only. Every envelope value is in a Markdown code span so nothing in a name or address is interpreted as Markdown. An address reads `Name <email>`, the name alone, or the email alone; the email is the SMTP address when there is one, and never an Exchange distinguished name. A message with no envelope fields and no body gets the heading alone. Since v0.1.36 a `cid:` link in the converted Markdown is rewritten to a relative link to the extracted attachment (`attachments/<name>`, percent-encoded) when exactly one extracted attachment of that message has the content ID; any other `cid:` link stays as written (see `attachments/` below).
- `body.html`, `body.rtf`, and `body.txt` are the original body forms, kept byte for byte whenever the message has them, whether or not that form was used: the native HTML as stored (or, when there is none, the HTML recovered from the RTF, as UTF-8), the decompressed RTF, and the plain-text body. They are exempt from the file contract's UTF-8 and LF rules, because they are copies of source content.
- `attachments/` (since v0.1.34) holds the message's by-value attachments, one file per attachment under its planned name (the naming rules decide the name; duplicates are numbered). Each is copied from the `.msg` to the staging directory in chunks of 256 KiB and hashed as it is written, so memory does not grow with attachment size; the size and SHA-256 recorded in `metadata.json` are those of what was written, and the number of bytes copied is checked against the length the `.msg` declares. Within a message the attachments are staged first, then `metadata.json`, then `message.md` and the kept body files. A zero-byte attachment is written as an empty file. An attachment that is not extracted is recorded with a reason: `embedded_depth_capped` (an embedded message nested past the depth cap), `ole_object`, `by_reference`, `method_none`, `method_unrecognized`, `method_unreadable`, or `embedded_message_unreadable`. A by-value attachment whose data is missing, unreadable, or of another length than declared is recorded as `failed` (`data_stream_missing`, `data_read_failed`, `data_length_mismatch`) and the export goes on. A message none of whose attachments is extracted has no `attachments/` directory. Since v0.1.36 each attachment record has `inline`, true when a `cid:` link in the body names its content ID, and a `cid:` link in `message.md` is rewritten to `attachments/<name>` when exactly one extracted attachment of the message has that content ID (compared without case, angle brackets, or `%XX` escapes); a link that matches no attachment, matches only attachments that were not extracted, or matches more than one extracted attachment stays as written and is counted by reason. `body.html` is never changed.
- An embedded message (an attachment that is itself a message) is written as a nested message directory at `attachments/<name>/` (since v0.1.35): its own `message.md`, `metadata.json` (the message schema, with `kind` `embedded_message` and `source_file` the outer `.msg`), kept body files, and `attachments/`, which may hold further embedded messages, down to the planner's depth cap (three levels in full). A message at the next level gets a directory with a `metadata.json` that records its subject, its direct attachment count, status `partial`, and the reason `embedded_depth_capped`, and nothing else; its parent's attachment record says `not_extracted` with that reason. The parent's record for an embedded message that was written has the method `embedded_message`, status `extracted`, and the directory name as `file` (no size or hash). An embedded-message attachment whose storage cannot be opened as a message stays a file attachment recorded as `embedded_message_unreadable`.
- `metadata.json` records the source file name (never a path), subject, Internet message ID, time, how the directory name was derived, a `body` object (the source used; the converter and version; the preprocessing steps that changed something; the Internet code page; each kept original file with its size, SHA-256, and a note; the number of `cid:` references and how many of them were rewritten and how many were not, by reason; and the formatting loss as `{reason, count}` pairs from a closed list), an `envelope` object (sender and "on behalf of" identity with display name, address type, address, and SMTP address kept separate; each To/Cc/Bcc recipient; submit and delivery times as stored ticks plus one UTC string; importance and sensitivity as stored integers; conversation topic and index; transport headers verbatim), an `attachments` array (one record per attachment, in storage order: the source name and what the naming rules did to it, the method, the content ID, whether a `cid:` link in the body names it (`inline`), a status of `extracted`, `not_extracted`, or `failed` with a reason, and for an extracted one the file name, size, and SHA-256), the number of attachments **not extracted**, and a status of `partial` with the reasons (always `other_properties_not_preserved`; also `attachments_not_extracted` when any attachment is not extracted, and unconverted HTML/RTF bodies when an HTML or RTF form existed but the body used is plain text or none).
- Everything is deterministic: no absolute paths and no export-time values, so exporting the same input twice gives byte-identical trees. The output reports `export_tree_sha256`, one hash over the whole tree, so two runs can be compared at a glance.
- Safety: the target `<dir>/<input name>/` must be absent, empty, or an archive that `tsp` wrote for the same source (same kind and name; the content hash is deliberately not compared, so re-exporting a changed source works). A directory `tsp` did not create, or an archive of a different source, is refused even with `--overwrite`. Files this export would change are replaced only with consent. Unrelated files inside an archive are left alone and counted.
- A plan that breaks a gate (for example a path over the 259-unit budget) is refused before anything is written; choose a shorter `--out`. The output path itself must leave room for the `.tsp-tmp` staging directory (about 239 units at most).
- Each file is written under a short numeric name in `<dir>/.tsp-tmp/` as it is rendered and renamed into place after the consent decision, so a partly written file never appears under its final name. `<dir>` and `.tsp-tmp` are therefore created before consent is decided; a refused run deletes the staged files, the staging directory, and `<dir>` itself if this run created it and it is empty. A target that `tsp` did not create is refused before anything is staged (its preflight counts print as zero). The archive as a whole is not all-or-nothing. After writing, every file is streamed through the hasher and compared with the manifest (`export_readback_mismatches`).
- Archives written by an earlier version are drafts and are replaced by re-exporting (with consent, or `--overwrite`): v0.1.31 changes `message.md` and `metadata.json` for every message and adds the `body.*` files; v0.1.34 changes `metadata.json` for every message (the `attachments` array) and the root `folder.json` (counts and tool version), and adds the attachment files; v0.1.35 adds the directories of embedded messages and changes the attachment records and the root `folder.json` counts of messages that have them; v0.1.36 adds `inline` to every attachment record and the rewrite counts to the `body` object, and changes `message.md` wherever a `cid:` link resolves.

## Output format

Reports are `key=value` lines (plus grouped `key field=value` lines for per-class / per-scope breakdowns). Keys are a **stable output vocabulary**: they are unchanged across versions so that outputs from different versions and modes can be diffed mechanically. The default `.msg` report is identical in shape to the report the `msg_parser`-based default produced before M3f, with one deliberate extra key (`attachments_data_stream_missing`, a custom-path-only anomaly signal; 0 on the verification corpus). The `--dry-run` report adds its own `plan_*`, `source_*`, and `folder_identity_*` keys, an export prints `export_*` keys (target state, preflight counts, consent, result, files written, plain bodies by kind, the body source used, the original body files kept, the formatting loss by reason, the `cid:` references, the attachments extracted and not extracted and their bytes, read-back mismatches, tree hash), and `--verify-envelope` prints per-field `*_match`/`*_mismatch` counts, `*_match_both` / `*_match_email_address_only` / `*_match_smtp_only` tallies for emails, and `*_present_total` counts.

The body keys of an export are `export_bodies_plain_present`, `export_bodies_plain_empty`, `export_bodies_plain_absent`, `export_body_source_native_html`, `export_body_source_rtf_html`, `export_body_source_plain_text`, `export_body_source_none`, `export_body_files_kept_html`, `export_body_files_kept_rtf`, `export_body_files_kept_txt`, one `export_body_loss_<reason>` per loss reason (`tables_flattened`, `rtf_not_converted`, `undecodable_bytes_replaced`, `invisible_padding_removed`, `html_conversion_failed`, `rtf_decompression_failed`), and `export_body_cid_references_total`; all are always printed, zero when not applicable.

The attachment keys of an export are `export_attachments_extracted` (by-value attachments written to files), `export_attachment_bytes_extracted` (their total size in bytes), `export_attachments_failed` (by value, but the data was missing, unreadable, or of another length than declared), and `export_attachments_not_extracted` (planned attachment files that were not written: not extracted by design, failed, or inside an embedded message that was not written; the failed ones are counted in both). The embedded-message keys are `export_embedded_messages_extracted` (nested message directories written in full), `export_embedded_messages_not_extracted` (planned embedded messages not written in full: at the depth cap, unreadable, or inside one of those), and `export_embedded_body_loss_total` (the formatting-loss count summed over the bodies of the embedded messages written; the per-reason body counters cover top-level messages only).

The `cid:` keys of an export (since v0.1.36) are `export_cid_rewritten` (links in the `message.md` of top-level messages rewritten to an extracted attachment), `export_cid_unresolved_no_attachment`, `export_cid_unresolved_not_extracted`, and `export_cid_unresolved_ambiguous` (links left as written, by reason), which sum with it to `export_body_cid_references_total`; `export_attachments_inline` (top-level attachments whose content ID a link names); and, for embedded messages, `export_embedded_cid_rewritten`, `export_embedded_cid_unresolved` (the three reasons summed), and `export_embedded_attachments_inline`.

Input that cannot be read is counted, never silently left out (since v0.1.37). A dry run prints `source_open_errors` (`.msg` files and directory entries that could not be opened or read, and PST folders below the 128-level folder limit) and `source_directories_beyond_depth_cap` (directories below the 64-level scan limit that were not entered); an export prints `export_source_open_errors` and `export_source_directories_beyond_depth_cap` with the same meaning and, when either is above zero, a warning on standard error: that input is not in the archive. A single `.msg` file that cannot be opened is an error instead. The PST diagnostic counts folders below the limit in `folder_open_errors`.

Every counter is either an aggregate count, a bounded MAPI vocabulary value (message classes, property IDs/types, attach methods, recipient types, property-set labels, CLSIDs, code page numbers), or a size in bytes — never user content. Anything the tool cannot classify is counted (`*_unrecognized*`, `*_errors`, `*_unknown`, `entry_accounting_gap_total`, `*_unsupported_codepage*`) rather than silently dropped, so nothing disappears without a trace.

## Architecture (modules under `src/`)

Since v0.1.20 the code is split into modules (every item is `pub(crate)` and each module imports exactly what it uses); the planning modules were added by v0.1.22, the export modules in v0.1.23, the envelope modules in v0.1.25, the de-encapsulation and bake-off modules in v0.1.26 to v0.1.28, the body module in v0.1.30, and the layout constants in v0.1.37:

1. **`main.rs`** — module declarations and `main()`, which dispatches on the arguments and input kind.
2. **`cli.rs`** — `Args`, `InputKind`, `classify_input`.
3. **`shared.rs`** — the `CompoundFile` alias, the MS-OXRTFEX `\fromhtml1` encapsulated-HTML check (`check_compressed_rtf_bytes`), MAPI property / recipient-type / attach-method constants, the traversal depth limits (`MAX_DIRECTORY_DEPTH`, `MAX_FOLDER_DEPTH`), `is_msg_file`, the one bounded and panic-contained RTF decompression (`decompress_rtf_bounded`, `MAX_DECOMPRESSED_RTF_BYTES`), `run_contained` (the one place that silences the panic hook), and the shared counters (`BodyCounters`, `CountStats`, `ZeroByteStats`) used identically by the PST and MSG paths so the two adapters cannot drift apart.
4. **`pst.rs`** — the PST diagnostic: walks the IPM subtree via `outlook_pst` and counts message classes, body availability (plain / native HTML / HTML encapsulated in RTF), recipient types, and attachment methods.
5. **`msg_report.rs`** — the shared MSG report shape (`MsgTotals`, `print_msg_report`), populated by the custom path.
6. **`oxmsg_classify.rs`** — the custom MS-OXMSG parser's container naming conventions and entry classification (`classify_oxmsg_entry` and friends).
7. **`oxmsg_decode.rs`** — property stream and value decoding primitives: typed fixed values, UTF-16LE decoding, the `PT_STRING8` code page chain and decoders, named-property decoding, and two stream-length helpers: a stream's length from its directory entry (`stream_len`) and a chunked read-through that counts bytes without holding them (`drain_stream_len`).
8. **`oxmsg_structure.rs`** — structural accounting: the two-pass walk (classify entries, then decode properties streams), `OxmsgTotals`, and the breakdown report printed by `--verify` when a gate fires.
9. **`oxmsg_extract.rs`** — the extraction layer (`extract_*`, `open_embedded_message`, `run_msg_extract`) that feeds both the default report and `--verify`, and `read_body_forms`, which reads the body forms (plain text, native HTML bytes, the Internet code page, the decompressed RTF) for the export; `read_body_forms_at` reads them for a message nested under a given storage (M4f-2a).
10. **`oxmsg_envelope.rs`** — envelope extraction (M4d): the sender, sent-representing identity, To/Cc/Bcc recipients, times, importance, sensitivity, conversation fields, and transport headers, from the message's properties and recipient storages, using the string code page chain. Nothing is derived or repaired. `extract_envelope_at` reads the envelope of a message nested under a given storage, with its own recipients (M4f-2a).
11. **`verify.rs`** — differential verification: comparison types, `collect_msg_verify_totals`, `print_msg_verify_report`, the structural gates (`structural_gate_values`).
12. **`verify_envelope.rs`** — `--verify-envelope`: the envelope comparison with `msg_parser` (subject, sender, recipient lists, names and emails, with the email tally by property) and the presence counts.
13. **`naming.rs`** — pure naming rules for archive paths: sanitizing, Unicode normalization, truncation to a unit budget (UTF-16 units, never splitting a character), reserved-name handling, and the collision key.
14. **`plan.rs`** — the pure export planner and its verifier: from a source tree (`SourceFolder`, `SourceMessage`, `SourceAttachment`) and a `Policy` (root length, 259-unit budget) it produces the list of planned entries with final names, flags, and counters, and `verify_plan` checks the gates (collisions, over-budget paths, invalid names, unit mismatches). No I/O.
15. **`source_msg.rs`** / **`source_pst.rs`** — read a `.msg` input (file or recursive directory) or a PST into the planner's source tree, plus the content-free source census. `source_msg.rs` also maps each message to its file and opens one message's content for export (`open_message`: the content, which includes the body forms, the envelope, and a descriptor for each attachment, together with a handle that streams one attachment's data at a time and opens an embedded attachment as a nested message through that handle (`open_embedded`, M4f-2a); `read_message_content` returns the content alone).
16. **`dry_run.rs`** — `--dry-run`: plan, verify, and print the census; also the input-name helpers (`root_stem`, `input_leaf_name`, `root_units`, `classify_source`) and subject-marker handling.
17. **`model.rs`** — the normalized model so far: `MessageContent` (subject, Internet message ID, time, the body forms as stored, the envelope, and the attachment descriptors) with `BodyForms`, `Envelope`, `Address`, `Recipient`, and `AttachmentInfo` (an attachment's method, content ID, and declared data length, never its bytes). The rest of the model (the property bag, embedded messages) is still M4b-4.
18. **`archive.rs`** — pure rendering of `message.md`, `metadata.json`, and `folder.json` (draft schemas), including the envelope header list, the FILETIME-to-UTC conversion, and the body outcome (what is selected and converted, the original body files to keep, and the `body` object), the attachment records of `metadata.json`, and the resolution of a message's `cid:` links against those records (`link_cid_references`); no I/O.
19. **`body.rs`** — the pure body pipeline (M4e-2a): selection of the body form, preprocessing, the isolated `htmd` conversion, the invisible-padding rule, the `cid:` reference scanner (its count, the content-ID comparison, and the link to an attachment), and the formatting-loss vocabulary.
20. **`export.rs`** — the export writer: refuses a target it did not create, renders each message once into the staging area (`stage.rs`), preflights the manifest against the target, applies the consent rules, commits by renaming, reads back, and prints the `export_*` report. Memory holds one message plus the manifest, not the archive. Since v0.1.34 it also copies each message's by-value attachments to staging in chunks, one at a time and never held whole, before it renders `metadata.json`, which records them. Since v0.1.35 its child module `export/nested.rs` stages one message's files for both top-level and embedded messages and writes embedded messages as nested message directories (a message at the depth cap gets a `metadata.json` only). Since v0.1.36 it also resolves each message's `cid:` links once that message's attachments are staged, and renders `message.md` from the result.
21. **`bakeoff.rs`** — the HTML-to-Markdown bake-off (M4e-0, built and run): a `MarkdownConverter` trait, content-free scoring, synthetic cases, and (with `--features bakeoff`) adapters for the three candidates; its preprocessing is `body.rs`'s.
22. **`rtf_deencap.rs`** — pure MS-OXRTFEX de-encapsulation (M4e-1): recognition, an RTF tokenizer, `\*\htmltag` and `\htmlrtf` handling, the font table's code pages, `\uN` with fallbacks, bounds, and content-free diagnostics. Used by `body.rs`.
23. **`verify_deencap.rs`** — `--verify-deencap`: the de-encapsulation differential against `msg_parser`.
24. **`verify_bodies.rs`** - `--verify-bodies` (M4e-2c): the content-preservation check. Pure word extraction for the HTML (after the production preprocessing) and for the Markdown, the greedy in-order comparison with its counts, and the corpus mode that reads each message's body forms, runs `select_body` and the export's conversion, and prints counts; `--dump-bodies` writes the word lists of messages with a difference.
25. **`stage.rs`** - the staging area of the streamed export (M4h-0): writes each rendered file to `.tsp-tmp` under a numeric name and keeps a manifest (relative path, size, SHA-256, never the content), computes the tree hash from the manifest, commits by renaming the staged files into place (deleting the ones identical to the target), discards on a refusal, and reads back by streaming each file through the hasher. Since v0.1.34 `add_stream` copies a source stream (an attachment) into staging in 256 KiB chunks, hashing as it writes; a source that fails or has the wrong length is reported and nothing is staged for it.
26. **`tests.rs`** — most of the older unit tests: classification, decoding, counters, every verify-comparison outcome, synthetic ANSI fixtures, structural gates, retired-flag handling, and the corpus-gated regression test. The newer modules keep their tests beside their code.
27. **`verify_attachments.rs`** - `--verify-attachments` (M4f-2c): hashes each top-level by-value attachment through the export's own reader (`MsgAttachments::open_data`, in chunks) and compares the SHA-256 and length with `msg_parser`'s payload by position, with an order-free comparison beside it and a gate total; counts only.
28. **`layout.rs`** - the archive's fixed names (`folder.json`, `message.md`, `metadata.json`, `attachments`). The planner derives its path-budget tails from their lengths, and `archive.rs`, `body.rs`, and the writer use the same constants, so renaming one cannot leave a stale number behind.

External crates: `outlook-pst` (PST), `cfb` (generic MS-CFB container), `compressed-rtf` (MS-OXRTFCP), `msg_parser` (oracle for `--verify` and `--verify-envelope` only), `htmd` (HTML to Markdown, pinned `=0.5.4`), `unicode-normalization` (naming), `serde` and `serde_json` (the archive's JSON), `sha2` (SHA-256 for the source, tree, and kept-file hashes), `clap`, `anyhow`; `proptest` for tests.

## Privacy design rules

- Never print input paths, display names, subjects, bodies, addresses, attachment filenames, or entry IDs — including in error messages.
- Message-class names, property IDs/types, CLSIDs, and code page numbers are treated as bounded vocabularies, not content, and may be reported by value.
- `--verify`, `--verify-envelope`, `--dry-run`, export, and the default extraction read real content (and, for planning, names) into memory to compute booleans, counts, and match counts, but never print it.
- An export writes message content only into the directory the user names, and records no absolute path and no export-time value in the archive.
- Loss must be explicit: every unreadable, unrecognized, or unresolvable item increments its own counter, and an export records what it did not extract and what formatting the conversion lost.

## Known limitations

- Neither M1 nor M2 nor M3 yet proves complete extraction fidelity. The export is a walking skeleton that has grown an envelope, a body, by-value attachments, and embedded messages (as nested folders, to the depth cap): OLE objects, by-reference attachments, the remaining properties, and PST input are not exported (each is counted or recorded as not extracted). Named-property normalization (decoding and resolution verified on the MSG side) feeds nothing yet.
- The body path (v0.1.31) was run on the real corpus (34 messages) and reconciles; the owner review of exported messages is pending, and only one invisible-padding run was removed where at least two were expected (unchecked). Not yet confirmed on real data: native HTML (the corpus has none, so the path has only synthetic tests), a string-typed `PidTagBodyHtml` (not read at all), `rtf_decompression_failed` (zero in the corpus), an RTF without encapsulated HTML (three corpus messages: they fall back to the plain text and are recorded as `rtf_not_converted`; the RTF itself is not converted), and the content-preservation check on bodies from other producers (on this corpus `--verify-bodies` found no difference over 31 HTML bodies, but it checks the Markdown against the HTML after the export's own preprocessing, so text the preprocessing removes is not covered). `cid:` images display from `message.md` only where the `cid:` reference was rewritten to an extracted attachment file (since v0.1.36; all 26 references in the corpus were); an unresolved reference stays as written.
- **Streamed export, what remains.** Since `v0.1.33` the export holds one message plus a small manifest (about 100 to 150 bytes per file) in memory, not the archive; the peak was flat at about 520 MB from 20 to 300 messages of about 45 MB each. Not yet tried: tens of thousands of files in the one flat staging directory (1,201 were), a manifest of millions of files (it is not spilled to disk), and real PST content. A whole message's content is still read into memory while it is rendered (the attachment bytes are not: since v0.1.34 they are copied in chunks, one at a time), and a PST reader must read messages lazily (M4i). A repeat export writes every unchanged file to staging before finding it identical (it deletes them again; the shortcut, option E, is not built). The 300-message run took about 3.0 s per message against about 1.9 s at 20 and 50 messages (cause not measured; disk and antivirus load are the likely reason). The export still replaces files one at a time rather than all-or-nothing (an interrupted run leaves the root `folder.json` marked `incomplete`).
- **Attachments (v0.1.34), what is and is not shown.** Shown (synthetic, 2026-10-18): peak working set 28 MB and peak paged memory 25 MB for 3 messages whose by-value attachment was 1, 50, and 200 MB each, and the 200 MB attachment's SHA-256 in `metadata.json` equals `Get-FileHash` of the exported file. Since run (2026-10-20, with M4f-2a and M4f-2c): an export of the real corpus with attachments (217 files, 0 read-back mismatches; 32 attachment files extracted, 6,282,892 bytes), the SHA-256 comparison with `msg_parser`'s payloads (30 of 30 top-level by-value attachments match), and `verify-split.ps1` (IDENTICAL). Not run: the adversarial-name fixtures beyond duplicate and missing names. Not tried: an attachment of gigabyte size (the largest streamed was 200 MB), and thousands of attachments in one archive (the flat staging directory and the manifest are untried at that scale; a repeat export also copies every attachment into staging before finding it identical, which matters more now that attachments dominate the archive's bytes). The length check against the container's declared length should never fire with `cfb` (a stream reads to its declared length or fails); it guards other sources. Zero-byte by-value attachments are written as empty files and show as `bytes: 0`; since v0.1.36 an attachment is marked `inline` when a `cid:` link in the body names its content ID, and that link is rewritten when exactly one extracted attachment has the ID (26 of 26 on the corpus; a percent-escaped, non-ASCII, or shared content ID, a `cid:` link inside an embedded message, and reference-style `cid:` links have not been seen on real data).
- The accepted file-contract ADR fixes the rules every archive file follows, but the field-level schemas are still drafts (`0.1-draft`) until the metadata stage (M4g); archives written now are expected to be re-exported.
- The envelope is checked against `msg_parser` for the subject, sender, and recipients on all 34 messages (0 mismatches); sent-representing, times, importance, sensitivity, conversation fields, and transport headers have no oracle. Importance low = 0 and normal = 1 are not in Microsoft text seen. In the five cases where the two email properties differ, `msg_parser` chose the SMTP address, which is what `message.md` shows; the rule is inferred from those cases. The `EX`-address-without-SMTP, unlisted-recipient, and flagged-recipient-type paths have no real instance in the corpus and are covered by unit tests only.
- Part of the accepted identity ADR is a decision without code: folder and PST message identifiers and the content hash are not yet written to the archive.
- The accepted naming ADR depends on rule L4 steps 4 and 5 (flattening over-budget folder chains; a hash-based last-resort name), which are not implemented: an entry that cannot fit is reported over budget and the export refuses.
- The accepted naming ADR's opt-in `--long-paths` and `--max-relative-path N` are not implemented: the path budget is fixed at 259 UTF-16 units, and a plan that does not fit is refused.
- `msg_parser` exposes only To/Cc/Bcc, so an ORIG-classified recipient (sender, MS-OXOMSG value 0) cannot be detected through it; the PST side and the custom path both track it. The export lists only To/Cc/Bcc recipients and counts any other row in `recipients_unlisted`.
- The in-house RTF de-encapsulation (`rtf_deencap.rs`) is built, tested, and now used by the export; on the corpus every difference from `msg_parser`'s HTML was traced to `msg_parser`. Its limits: Windows-1255 and any other code page the project does not decode become U+FFFD (1 byte in the corpus); line-break placement has no independent oracle; encapsulated plain text (`\fromtext`) is not handled. It supports only the code pages the `PT_STRING8` decoders implement; other bytes become U+FFFD and are counted. The recovered HTML is UTF-8 text whose `charset=` declaration, if any, is stale. The decompressed RTF comes from `compressed-rtf`, which returns a string (so an RTF with bytes that are not valid UTF-8 would fail to decompress and be recorded as `rtf_decompression_failed`).
- `PT_STRING8` decoding implements Windows-1252, ISO-8859-1, US-ASCII, and UTF-8. Any other code page decodes only all-ASCII input (and only for a known ASCII-superset code page) and is otherwise reported as unsupported; no text is produced. The corpus contains no `PT_STRING8` value, so decoding has been exercised only by synthetic fixtures. (Code page *resolution* has met real data: all 29 corpus files resolved from a real code page property.) See `docs/verification/m3-results.md`.
- PST table reads assume `PidTagRecipientType` / `PidTagAttachMethod` / `PidTagAttachSize` arrive as 32-bit integers; a different encoding falls into the "unknown" bucket rather than miscounting, but the assumption has never been falsified by contrary data.
- **Password-protected PSTs are not supported yet, and supporting them is a requirement for M4i.** `tsp` neither reads `PidTagPstPassword` nor accepts a password, so it does not check one and does not report that a PST has one. The password is advisory (MS-PST: a CRC-32 of it is stored in the message store and enforced by the client; neither encoding method uses it), so `outlook-pst` is expected to open such a file without it, but no password-protected PST has been run. A PST whose header marks its data as Windows Information Protection encrypted (`bCryptMethod` 0x10) is a different case: `outlook-pst` does not know that method, so such a file fails to open with a generic error, and no password changes that.
- The diagnostic opens embedded messages one level deep only (it reads the nested message class); the export reads them up to eight levels and writes three levels as nested folders (a message at the cap gets a `metadata.json` only). The PST side cannot open them at all (P4c); in a PST dry run they are counted as `source_embedded_attachments_not_opened` and planned as plain attachment files.
- The structural breakdown that `--verify` prints when a gate fires has never fired on real data, because the corpus is clean; it is exercised only by a test that prints it for empty totals.
- The planner shortens names only down to fixed floors. When a very long `--out` path leaves too little room, entries are reported over budget (`plan_gate_over_budget`) rather than shortened further, and an export refuses such a plan; the PST fixture shows this with a deliberately long output path (see `docs/verification/m4-results.md`). The `.msg` directory has been planned and exported at a short output path with no violations; the PST has not been run at a short output path yet.
- The PST dry-run counts (10 folders, 60 messages, 84 attachment files) differ from the earlier PST diagnostic figures (10 folders including the root, 57 messages, 79 attachments). The difference has not been reconciled.
- All MSG verification runs against one 29-file corpus (plus its subdirectories for the dry run and export), with `msg_parser` as the only oracle. No comparison against an independent PST implementation, or against `libpff`/`libpst` for either format, has been run.
