## Decisions in force (project owner, 2026-09-30)

- Staged order: module split first, walking skeleton before breadth.
- **Layout stays as the accepted ADR [Deterministic Markdown archive](../../ADRs/deterministic-markdown-archive.md) chose:** one folder per message containing `message.md`, `metadata.json`, and an `attachments/` subfolder. That ADR is not superseded. The message folder's name mirrors the message subject; `attachments/` is a literal name.
- Export mirrors the PST folder tree. Root is `<out>/<PST file stem>/` (sanitized) so several PSTs can share one `<out>`.
- Duplicates: one uniform, zero-padded suffix for folders, messages, and attachments. The first item in a group keeps the bare name; the k-th is ` (kk)`, at least two digits, widened per group beyond 99, in deterministic (time, identifier) order. There is no ` - Copy`; content identity is recorded in metadata (`content_sha256`, `identical_to`), never in names.
- Metadata lives alongside the item it describes: `metadata.json` in a message folder, `folder.json` in a folder directory.
- Replacement characters as in rule N3; scope: everything reachable from the IPM subtree, non-mail items as metadata stubs; inline attachments stay in `attachments/` and are marked `inline`.
- Overwrite safety: `tsp` warns (counts only) and asks permission, or exits.
- Path budget: default 259 units from the real root; `--long-paths` opt-in; `--max-relative-path N` for archives that will move; the longest relative path is recorded and reported.
- Folder marker files: `folder.json` in every folder directory.
- The source file's SHA-256 is recorded in the root `folder.json` by default; `--no-source-hash` skips it.
- Non-PST inputs: a directory of `.msg` files exports to `<out>/<directory name>/` and **mirrors its subdirectories as folders** (export only; the diagnostic's non-recursive scan is unchanged); a single `.msg` exports to `<out>/<msg file stem>/`.
- Path length is handled up front, using UTF-16 code unit counts and worst-case child reservation.
- Approved dependencies: `serde`, `serde_json`, `sha2`, `unicode-normalization`, and `proptest` (dev-only). The HTML-to-Markdown bake-off is approved. 2026-10-12: the owner accepted `htmd` pinned `=0.5.4` as the converter, subject to acceptance of the converter ADR.

## What changed from v4.22

1. **M4f-1 is built and tested (release `v0.1.34`, from `v0.1.33`).** The export writes each top-level message's by-value attachments to `attachments/<planned name>`. New: `Stager::add_stream` in `src/stage.rs` (copy a source stream to staging in 256 KiB chunks, hashing as it writes); `AttachmentInfo` and `MessageContent.attachments` in `src/model.rs`; `open_message`, `OpenMessage`, and `MsgAttachments` in `src/source_msg.rs`; `AttachmentRecord`, `method_label`, the `attachments` array in `metadata.json`, and `RootCounts.attachments_extracted` in `src/archive.rs`; `stream_len` and `drain_stream_len` in `src/oxmsg_decode.rs`; `PROP_ATTACH_DATA_BINARY` in `src/shared.rs`. Changed: `src/export.rs` (the staging order and three new report keys), `src/oxmsg_extract.rs` (the zero-byte check drains the stream in chunks), the `hello` metadata golden file (`"attachments": []`), and the ignored generator (`TSP_BIG_ATTACH_MB`). `read_message_content` is kept as a content-only wrapper over `open_message`. `Cargo.toml` is bumped to 0.1.34 in the tagged commit.
2. **The choice, taken as recommended (2026-10-18): copy in chunks, not hold one attachment in memory.** Reasons: memory is a constant instead of the largest attachment in a corpus whose sizes are not known (a whole-stream read with doubling growth needs roughly 1.5 to 2 times the attachment transiently; an estimate, not measured); the copy is a single pass that hashes as it writes; the rest of `stage.rs` already streams; and the cost over holding one attachment is small, because both need the model to carry descriptors and the bytes to be read at staging time. Costs accepted: a second write path beside `Stager::add` (guarded by a test that both give the same manifest entry, file, and tree hash), and cleanup of a partly written file when a read fails.
3. **Decisions taken with it, as recommended:** the model carries attachment descriptors, never bytes; within a message the attachments are staged before `metadata.json`, because it records each size and hash; a by-value attachment whose data is missing, unreadable, or of another length than the container declares is recorded as `failed` and the export goes on (only a failure to write to staging stops it); OLE, by-reference, and method none, unrecognized, or unreadable attachments are recorded as `not_extracted` with a reason; embedded messages stay `not_extracted` (`embedded_message`) until M4f-2, where they become nested message folders at the depth cap.
4. **A refinement of the recommendation, found while drafting:** the zero-byte check in the diagnostics (`extract_attachment_method_counts`) held every by-value stream whole just to test whether it was empty. Replacing it with the directory entry's length would have stopped it noticing a data stream with a broken sector chain (today `zero_data_stream_missing`), so it reads the stream through in chunks (`drain_stream_len`): the same answers with constant memory. The directory entry's length (`stream_len`) is used only as the export's declared length.
5. **Results (2026-10-18).** (a) Built; 332 tests pass and 1 is ignored (321 plus 11 new: 4 for the stager's chunked copy, 2 in `source_msg.rs`, 2 in `archive.rs`, 3 in `export.rs`); `cargo fmt --check`, `clippy -D warnings`, and CI were not reported. (b) Memory gate, synthetic (3 messages, each with one by-value attachment of 1, 50, or 200 MB; `measure-peak.ps1`): peak working set 28 MB and peak paged memory 25 MB at all three sizes, exit code 0, 16 files written (the root `folder.json` plus, per message, `message.md`, `metadata.json`, `body.html`, `body.txt`, and the attachment), 0 read-back mismatches, 0.4, 1.1, and 2.8 s; the tree hashes are in `docs/verification/m4-results.md`. (c) By hand: the SHA-256 recorded in `metadata.json` for the 200 MB attachment equals `Get-FileHash` of the exported file.
6. **What these results do not show.** No real-corpus export with attachments has been run, so there is no corpus tree hash for `v0.1.34`, no count of corpus attachments extracted, and `verify-split.ps1` has not been run (the diagnostics' answers should be unchanged, which it would confirm); the M4f gate's differential (SHA-256 against `msg_parser`'s payloads) is not built; the adversarial attachment fixtures are only partly covered (duplicate and missing names, empty data, missing data, other methods, but not reserved names, 255-character names, case-only differences, or control characters); the largest attachment streamed is 200 MB and the gate used 3 messages, so neither a gigabyte attachment nor thousands of attachments in one archive (the flat staging directory and the manifest) are tried; the 28 MB peak says nothing about the 520 MB of M4h-0, which came from converting a 25 MB body (the body size of the gate corpus was not reported); the declared-length guard has only been exercised by a stand-in reader, since `cfb` reads a stream to its declared length or fails.
7. **Behavior and format changes, in force.** `metadata.json` of every message gains the `attachments` array (draft schema); `attachments_not_extracted` now counts attachments whose status is not `extracted`, and the status reason `attachments_not_extracted` is listed only when that count is above zero; the root `folder.json` counts gain `attachments_extracted`, and its `attachments_not_extracted` means planned attachment files not written (including failed ones and those inside embedded messages); `attachments/` files appear in the archive; the report gains three keys, and `export_attachments_not_extracted` now has the meaning just given; archives written by earlier versions are replaced by re-exporting. No consent, ownership, or staging rule changed. The choices are recorded in the new ADR [Attachment extraction: chunked copy, per-attachment records, and failure handling](../../ADRs/attachment-extraction-streaming-copy-and-records.md) (proposed; accepted when the owner commits it), with short amendments to the file-contract, output-posture, and body ADRs and notes in the archive, naming, and identity ADRs; the `attachments` record shape is part of the draft schema that M4g freezes.
8. **Premises the draft could not check, now resolved by the build and the tests:** that `cfb` 0.15 offers `Entry::is_stream` and `Entry::len`; that its stream reads in pieces (the copy loop handles short reads); that a stream returned as `impl Read` is usable after the container handle's borrow ends; that no other code built a `MessageContent` or `RootCounts` literal; and that the golden file edit matches the new output.

## What changed from v4.20

1. **M4e-2c is built and verified on the corpus (release `v0.1.32`, from `v0.1.31`).** New: `src/verify_bodies.rs` (`--verify-bodies`, `--dump-bodies`). Changed: `cli.rs` (the two flags; `--recursive` also applies to `--verify-bodies`) and `main.rs` (the module, the dispatch, the `--recursive` rule, and a refusal of `--verify-bodies` for `.pst` input). The export is unchanged, and `Cargo.toml` keeps its version because the root `folder.json` records it. The build is clean and 312 tests pass (293 plus 19 new).
2. **What it checks.** For each message whose selected body is HTML, it runs the export's own calls (`select_body`, `preprocess_html_detailed`, `htmd`, the padding rule) and compares the visible words of the preprocessed HTML with the words of the Markdown, in order. HTML words: text outside tags, without the content of a closed `head`, entities decoded (a named entity outside the built-in table is counted as `html_unresolved_entities_total`, not guessed), block elements and `br` separating words and inline elements joining them. ## Goal

Turn what the two adapters read into a durable archive: a Windows-safe directory tree mirroring the source's folders, one directory per message named from its subject, with `message.md`, `metadata.json`, and `attachments/`, plus a `folder.json` per folder carrying identity, provenance, and loss status. M4 is the first milestone where `tsp` writes message content to disk; stdout stays counts-only.

## Where the code stands (v0.1.31, built from v0.1.30; corpus-verified 2026-10-14)

- The MSG adapter decodes typed properties, value streams, named properties, recipients, attachments (methods, content IDs, emptiness), one level of embedded message, and, since M4d, the envelope (`oxmsg_envelope.rs`). It reads content into memory and prints only counts.
- The PST adapter is a counter-only diagnostic over `outlook-pst` v1.2.0. It cannot open embedded-message or OLE attachments (P4c).
- `msg_parser` is an oracle for comparable MSG fields (`--verify`, and `--verify-envelope` for the envelope); no PST oracle has been run.
- The pure naming rules and export planner exist (`naming.rs`, `plan.rs`), and `--dry-run` plans an export of a PST, a `.msg`, or a directory of `.msg` files and prints a content-free census.
- **`tsp <msg|dir> --out <dir>` exports** `.msg` input: `message.md` (the subject as a heading, a list of the envelope fields the message has, and, since v0.1.31, the body: converted Markdown, else the plain text in a code fence), `metadata.json` (including an `envelope` object), and `folder.json` files, with preflight, consent, staged writes (since v0.1.33 each message is rendered once into the staging directory and only a manifest is kept in memory), and read-back. The schemas are drafts (`0.1-draft`). The model holds the message content and the envelope (`model.rs`); since v0.1.31 each original body form is kept as `body.html`, `body.rtf`, and `body.txt`; attachment bytes, the remaining properties, and PST export do not exist. The export was last run on the real `.msg` corpus at v0.1.23.1 and had not been reported for any tag between; v0.1.31 was run on the corpus on 2026-10-14 (34 messages, 171 files, `export_readback_mismatches=0`, tree hash `dafb3290...93c8`), and 293 tests pass. That hash was not reproduced on 2026-10-17 (builds of `v0.1.31`, `v0.1.32`, and `v0.1.33` all print `1daa76fc...f277d53f`); see What changed from v4.21, item 6.
- **Since `v0.1.34` (M4f-1)** the export also writes each top-level message's by-value attachments to `attachments/` (copied to staging in chunks, one at a time) and records every attachment in `metadata.json`; embedded messages, OLE objects, and by-reference attachments are recorded as not extracted. Tested (332 tests) and measured on synthetic input (peak memory flat at 28 MB for attachments of 1, 50, and 200 MB); not yet run on the real corpus.
- Fixtures: 29 `.msg` files at the top of the fixture directory (27 carry HTML only inside RTF; 23 attachments carry a content ID; 1 embedded message; 1 zero-byte attachment; no `PT_STRING8` value), more `.msg` files in 3 subdirectories (which the recursive dry run and export include, and the non-recursive `--verify` and `--verify-envelope` do not), and one enhanced PST.

## Working rules (unchanged)

- Staged, each stage with an evidence gate; done means met on Windows.
- Claude drafts uncompiled; the owner runs the quality gate and supplies output. Docs are updated per stage and separate verified from written.
- Stdout is content-free at every stage. Archive content goes only to the directory the user names.
- Loss is explicit: never silently dropped.
- Symmetry between adapters where the PST side allows.
- Sources of truth: Microsoft's specifications for formats and Win32 naming; independent implementations as oracles, not authorities.

### M4e-1 — MS-OXRTFEX de-encapsulation (in-house)

The specification pages this was written from (all read 2026-10-07): MS-OXRTFEX 2.2.3.1 (recognizing encapsulation: `{\rtf1` first; at most the first 10 tokens, begin-group marks and control words; `\fromhtml1` or `\fromtext` among them; any other token kind, or neither word, means ordinary RTF), 2.2.3.2 (extracting encapsulated HTML), 2.1.3.1.4 (the HTMLTAG destination group, whose numeric parameter is ignored), and 2.1.3.1.5 (the MHTMLTAG group, covered by the rule that ignorable destinations other than HTMLTAG are skipped).

Decisions taken in the code, each stated so it can be overruled:
- **Recognition is the 10-token rule**, stricter than the whole-document `\fromhtml1` search in `shared.rs`. The two are compared by `--verify-deencap`; `shared.rs` is not changed.
- **Output is UTF-8 text.** A `charset=` in the recovered HTML is stale; `meta_charset_declared` records it and the body pipeline (M4e-2) must not trust it.
- **`htmltag` content** is decoded in the document's default code page; **ordinary text** in the current font's code page (from `\fcharset` or `\cpg` in the font table); the font is tracked inside `\htmlrtf` regions, as the specification says.
- **`\htmlrtf` is group-scoped** like any RTF character-formatting toggle. This is an assumption; a corpus disagreement with `msg_parser` that traces to it would show here first.
- **Code pages** are limited to those `oxmsg_decode` implements (1252, ISO-8859-1, US-ASCII, UTF-8). Anything else becomes U+FFFD per byte and is counted (`deencap_undecodable_bytes_total`, `deencap_unsupported_codepage_<n>_files`); no code page crate is added until the corpus shows it is needed.
- **Skipped destinations** are a fixed list of standard destinations without visible text, only as a group's first word; unlisted ones are treated as visible (a known limit).
- **Bounds:** group depth 1024 and output 64 MiB, each reported as a flag when hit; no input can panic it (a property test covers arbitrary bytes).
- The decompressed RTF still comes from `compressed-rtf`, whose result is a string; an RTF stream with raw non-UTF-8 bytes would fail decompression and be counted (`rtf_decompression_failed`). Replacing it with an in-house MS-OXRTFCP decompressor is a possible follow-up if the corpus shows it matters.

Gate: spec-derived unit and golden tests: **met**. Property test that arbitrary input never panics and stays within the output bound: **met**. Recognition rule confirmed against `check_compressed_rtf_bytes`: **met** (0 disagreements in 29 files). Weak-oracle differential against `msg_parser`'s `html_from_rtf()` on the 27 encapsulated-HTML messages, every disagreement triaged: **met**: the recovered HTML differs from `msg_parser`'s in all 27 pairs, and every difference was traced (with `--dump-deencap`) to `msg_parser`: it prepends the font table's text, inserts `*` after each tag group, drops line breaks, reads `\'hh` as Latin-1, emits `\uN` fallbacks instead of the Unicode character, and corrupts one word in one file (consistent with its wrong preset dictionary). After normalizing for those, 24 of 27 pairs are identical and the other three are explained by the fallback and dictionary faults. Details: `m4-results.md`.

Residual, not blocking: one byte of code page 1255 (Hebrew) is replaced by U+FFFD (the correct character is U+200F); no other unsupported code page appeared, so no code page crate yet. Line-break placement (CRLF from `\par` and line words inside `htmltag` groups, as MS-OXRTFEX describes) has no independent oracle. `\fromtext` encapsulated plain text (1 file) is not handled; the plain-text body already exists. The decompressed RTF still comes from `compressed-rtf`, whose result is a string.

### M4h-0 — streaming export (pulled forward from M4h; the owner chooses the approach)

Status: **built and verified (release `v0.1.33`, 2026-10-17), option C; see "What changed from v4.21".**

Why now: the export renders every file of the archive in memory (`render_archive` builds a list of all files with their content), compares each with the target (`preflight`), hashes them (`tree_hash`), writes them, and reads them back. Since M4e-2b the content includes every original body (the RTF is larger than the HTML it carries); M4f adds attachment bytes; the owner has PST files of several gigabytes, so memory would grow with the archive. What is already small and can stay in memory: the planned names, times, and identifiers (about the same size per message whatever its content). What must stop being held: file content.

Alternatives, with pros and cons:

- **A. Keep it, add a guard** (estimate the archive size and refuse above a limit, or an option for it). Pros: trivial, no risk. Cons: it does not solve the problem; a multi-gigabyte PST cannot be exported.
- **B. Render twice** (pass 1 renders each message and keeps only each file path, size, and SHA-256, comparing with the target for the preflight; pass 2 renders again and writes). Pros: memory is one message plus a small manifest; the consent rules and counts stay exactly as accepted; no extra disk. Cons: every message is read, converted, and hashed twice (the HTML conversion is the costly part), and for a PST the source is read twice; it relies on the rendering being deterministic (it is, and the tree hash tests it).
- **C. Stage, then commit** (render each message once, write its files to the staging directory under the existing short numeric names while keeping only a manifest of path, size, and SHA-256; compare the staged hashes with the target for the preflight; after consent rename the staged files into place and delete the ones identical to what is there; read back by streaming). Pros: each message is rendered once; memory is a small manifest; the preflight counts, consent rules, per-file atomic replace, `incomplete` marker, and staging naming stay as accepted; renaming on the same volume copies nothing, so a first export needs no extra disk beyond the archive itself. Cons: staged files with unchanged content occupy disk until the end of a re-export (up to the size of the files that are not new); a refused or interrupted run leaves staged files to clean (the cleanup rule exists); one directory with millions of numeric files may be slow on NTFS (shard it); the manifest grows with the file count (about 100 to 150 bytes per file, so a million messages is on the order of half a gigabyte; if that matters, spill it to a sorted temporary file).
- **D. Write as you go, with consent for the directory only** (no counts before writing). Pros: simplest, bounded memory. Cons: it contradicts the accepted output-posture ADR (counts before any write, nothing replaced without consent), leaves a partial archive after a refusal, and cannot tell identical files from changed ones.
- **E. Skip rendering when nothing can have changed** (if the root marker is for the same source with the same source hash and tool version and status `complete`, every file is identical, so write nothing). Pros: a repeat run is instant. Cons: only a shortcut: it needs the source hash (hashing gigabytes, and unavailable under `--no-source-hash`) and says nothing about a first or changed export. It can be added to B or C later.
- **F. Render in parallel** with a bounded queue and in-order commit. Pros: faster (conversion is CPU-bound). Cons: orthogonal to memory, and ordered output needs care; do it after B or C, not instead.
- **G. Build in a sibling directory and swap it in.** Pros: whole-archive atomicity. Cons: needs space for a second copy, a directory swap is not atomic on Windows, and it conflicts with preserving unrelated files and the consent rules.

Recommendation: **C**, optionally with E as a later shortcut and F after it; B as the fallback if staging proves awkward. Do it before M4f (attachments would otherwise be held in memory too) and before M4i. Source side for a PST: the planner needs every name, time, and identifier up front (small), and each message is then read lazily; attachment bytes are copied and hashed in chunks.

Gate for M4h-0: the streamed export produces a tree byte-identical to the in-memory export of the same input (same `export_tree_sha256`) on the corpus; all existing export tests pass except where they depend on the internals; the overwrite matrix is re-run; and a generated archive larger than the memory budget chosen for the test (for example thousands of synthetic messages with multi-megabyte bodies) exports with a working set that does not grow with the archive size, measured by the owner. **Met 2026-10-17:** the tree hash is identical to the in-memory export's on the corpus (and at 20 synthetic messages), the overwrite matrix was re-run by hand and by the tests, and a synthetic archive of 300 messages (about 19 GB written) exported with a peak working set of 523 MB against 521 MB at 20 messages, where the in-memory writer needed 1,668 MB at 20.

## Architecture note: separate crates (not a goal now)

The module split exists for navigability and so that new pure modules (`naming`, `plan`, the model) can be developed and tested without the adapters. It is not a first step toward a Cargo workspace. All items are `pub(crate)` because the split was mechanical, so the current boundaries are not a designed public API, and the crate is `publish = false`.

Crate boundaries become worthwhile only for a concrete reason: another program embedding the engine, enforcing that the model never depends on an adapter, isolating heavy dependencies (`outlook-pst`, `msg_parser`, an HTML converter) so they compile and change separately, or independent versioning. None applies today. Decision: stay a single binary crate through M4, keep `naming`, `plan`, and the model free of imports from `pst`, `oxmsg_*`, and `verify` (a test can check the `use crate::` lines), and revisit at M4j with evidence such as build times and the shape of the interfaces. If the boundary is ever drawn, a plausible set is: model, naming, and plan; the MSG adapter; the PST adapter; the archive writer; and the CLI with `--verify`.

## Principal risks

- **Naming policy** (M4a/M4b). Naming decides re-export stability; a wrong choice forces re-exporting archives. Mitigation: pure engine, census, property tests, and now an accepted ADR with its open confirmations listed.
- **Path budget in a directory-per-message layout.** Every message is a directory, so the 248 rule and worst-case child reservation bind tightly; long subjects plus long attachment names will be truncated often on long roots. The PST fixture already shows entries that cannot fit at a root of 152 units (4 of 154). Mitigation: budget from the real root, report truncation counts, `--max-relative-path`, guidance to export near a drive root. M4c refuses to export a plan that breaks a gate; whether a better answer exists (flattening, L4 step 4) is open.
- **Bodies** (M4e). De-encapsulation and HTML-to-Markdown quality on Word HTML; partly subjective. Mitigation: bake-off, content-preservation check, verbatim body kept. The corpus has no native HTML, so real-data evidence for the converter depends on the de-encapsulation or new fixtures. The bake-off's corpus-wide figures (2 words missing of 26,952 for the leading candidate) come from one producer, and its word metric does not check order; the converter choice therefore rests on the metric plus a by-eye review of a few messages, and layout tables are flattened by design.
- **PST attachments** (M4i). Blocked by the public API.
- **PST counts unreconciled.** The planner and the earlier PST diagnostic disagree on the fixture's size (see M4b-3); until resolved, the M4i reconciliation gate has no trusted baseline.
- **Folder identity.** Both identifiers were readable on the fixture; the NID-derived identifier is still unproven across other producers. The fallback ordering is deterministic but weaker.
- **Content-hash definition** (Q11) now affects only the `identical_to` metadata, not any name, so a poor first definition is cheap to correct.
- **Very large duplicate groups.** Thousands of same-subject messages in one folder widen their suffix and rename the group once when it crosses 99 or 999 members. Mitigation: per-group width, census counts of large groups (the fixture's largest group is 16).
- **Schemas frozen too early or too late.** M4c and M4d produce draft schemas ahead of the field-level freeze on purpose; the risk is treating them as final. They carry `schema_version` `0.1-draft`, and the accepted file-contract ADR says drafts carry no compatibility promise.
